# ADR 018: PDF documents rendered with @react-pdf/renderer, signed share links for service reports

**Status:** accepted · 2026-11-10 · implemented in 0.4

**Context.** Quotes, invoices and service reports need branded PDFs (FIN-04) that office staff download, the API
returns and customers open from the portal or an email (POR-04, AI-03). The documents are in English or Bahasa
Indonesia and in USD or IDR. The options were a headless browser printing HTML, a hosted PDF service, or a PDF
library in the app. The server has no swap and the web container a 512 MB limit, so a browser per render is too
heavy, and a hosted service would send customer data to another party. Customers who open the _Job completed_
email often aren't signed in to the portal.

**Decision.**

- `@react-pdf/renderer` (pinned) in a package of its own, `packages/documents`, with the quote, invoice and
  service report layouts as React components. The renderers take plain view models (`types.ts`) and never touch
  the database: the web app loads the data in a transaction, builds the view model, and renders after the
  transaction has ended, so no connection waits on a render. Rendering runs on request in the web server's Node
  runtime (`serverExternalPackages`); no PDF is stored.
- One font: Inter regular and bold (SIL Open Font License), subset to Latin and the symbols the documents use,
  embedded as data URLs generated by `pnpm --filter @fieldops/documents fonts`. The web app bundles the package,
  so a path to a font file would point inside the build output; a data URL needs no file or network at run time.
- Labels in English or Bahasa Indonesia, from the document's language: the customer's for quotes and invoices,
  the report's own for service reports. Money and dates are formatted with `Intl` like the app. Letter paper for
  USD organizations, A4 for IDR.
- The letterhead shows the organization's name and address with a monogram in its brand color, darkened until it
  reads as text on white (4.5:1). Logos aren't stored as files yet, so the monogram is always drawn.
- Tables repeat their header on every page they span, every page has a "Page n of m" footer, and invoices carry a
  PAID or VOID stamp.
- The service report embeds JPEG and PNG originals up to 4 MB (at most six photos, before ones first) and the
  signature. Other formats are left out rather than converted.
- Sending a report emails a link to `/share/reports/<token>`. The token is base64url JSON (organization, report,
  expiry in Unix seconds) followed by an HMAC-SHA256 of it, keyed with the app secret (`BETTER_AUTH_SECRET`) and a
  purpose prefix. It is valid for 30 days and nothing is stored. The route checks the signature in constant time,
  then serves the PDF only while the report is `sent`: an expired link answers 410, and a report changed after
  sending shows a short page saying it is being updated. Signed-in portal customers download the sent reports of
  their own jobs from the job page.

**Consequences.** PDFs need no browser, external service or font files, and the same input gives the same
document on every machine. Layouts are limited to what react-pdf supports (a flexbox subset, no CSS grid), and
scripts outside the Latin subset wouldn't render until the subset grows. Large photos are skipped, not resized, so
a report can lack a photo the job has. A share link can't be revoked on its own: it stops working when it expires,
shows "being updated" while the report is back in draft, and serves the latest sent version after the report is
sent again. Rotating the app secret invalidates every link, and every session with it.
