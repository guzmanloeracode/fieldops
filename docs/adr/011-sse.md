# ADR 011: Server-sent events instead of WebSockets for live updates

**Status:** accepted · 2026-11-10 · implemented in 0.3

**Decision.** Live updates for the notification center and the dispatch board use server-sent events from a
Next.js route handler (`GET /api/v1/stream`), fed by PostgreSQL `LISTEN/NOTIFY`, with a heartbeat every
25 seconds.

- Triggers on `job`, `job_assignment`, `time_off`, `expense_request` and `notification` call `pg_notify` on the
  `fieldops_live` channel with a small JSON message: organization, kind, id and, for notifications, the user.
  PostgreSQL delivers it only when the transaction commits, so a rolled-back change is never announced.
- Each web process holds one listening connection and forwards a message only to the streams of signed-in
  users in that organization (and notifications only to their recipient). Messages carry ids, never record
  contents; the page fetches what changed through the normal, permission-checked path.

**Why not Redis (planned for 0.3 in PRD §15.3).** With one web container, `LISTEN/NOTIFY` does the same job
without another service on a shared server with no swap. Rate limits use a PostgreSQL table for the same
reason. Redis comes back when there is a second web replica or a measured need.

**Consequences.** Works through Cloudflare and nginx (`proxy_buffering off` on `/api/v1/stream`, and the route
sends `X-Accel-Buffering: no`), with no separate WebSocket server. Seeds and resets run with `app.quiet` set, so
bulk writes publish nothing.
